## Selector library — core + Kotlin JDSL engine built & green (0.1.0-SNAPSHOT, 2026-10-20)

Third library: `selector/` with `selector-core` (stdlib) and `selector-jdsl` (Kotlin JDSL 3.9.0, the first line with Boot 4 support; pinned in the local catalog under `[versions]`, not Boot-managed). **Scope decided by Awais: the selector builds the WHERE clause and nothing else — sort moved to pagination** (`pagination.core.sort`: `SortableFields` = sortable names + tie breaker + default sort; `SortRequest.parse` of Spring's `sort=field,dir`, always ending with the tie breaker; a list therefore has two declarations, filters here and order there — accepted).

**Studied first:** rebuy's `selector` (QueryDSL + JDSL branches, 27 strategy classes in product-silo) and `sorter`. Kept: registry of one binding per field, dependency-free core value, one predicate out, typed parsing once. Rejected: unknown key silently ignored (typo returns the whole table), wrong value count → silent false predicate, the 2/3/4-part `filter.` key grammar with `*` wildcard, one Spring bean class per field per operator, global registry keyed by entity type, core tied to JDSL. `sorter` is 4 files, unused by the silos (they use Spring's Pageable sort — no whitelist, unknown property = 500, no tie breaker).

**Core:** `Field<T>(name, FieldType<T>, operators)` (no-operator field rejected; `like` only on STRING; name may not contain `.`/`,`/space); `FieldType` STRING/INT/LONG/BOOLEAN/UUID/INSTANT/OFFSET_DATE_TIME parses once with a plain message; `Operator` eq/ne/lt/lte/gt/gte/in/like by suffix; `FilterDefinition(fields)`; `Selection.parse(definition, params, reserved = {page,size,after,sort})` → `Condition<T>(field, operator, values)` (one value except IN). Grammar `field=v` (eq), `field.op=v`, `field.in=a,b,c`. EVERY mistake = `SelectorException(key, message)`: unknown field (lists fields), unknown/disallowed operator (lists allowed), unparsable value (type's message), empty value, key twice, malformed key. 23 core tests.

**JDSL engine:** `JdslBindings<E>(definition) { bind(field, E::prop); strategy(field) { condition -> … } }` — explicit, one line per field; **the compiler checks `Field<T>` against `KProperty1<E, T?>`**; builder refuses unbound, twice-bound, or foreign fields. `Jpql.where(selection, bindings): Predicatable?` — AND of per-condition predicates, null when empty (JDSL's `where(null)` skips the clause). Values are bound parameters (asserted on the captured SQL: `where (l1_0.status=?) and (l1_0.price<?)`). Ordered comparisons satisfy JDSL's `T : Comparable<T>` with an erased placeholder type (JDSL never reads the type parameter). `JdslStrategy = Jpql.(Condition<*>) -> Predicatable` is the escape hatch (test: `search` field with no column → `title like %…%`). Reflection binding was tried and dropped: JDSL's `path(KProperty1)` casts to `CallableReference`, so only compiler-generated references work — the explicit builder is better anyway (type check, no kotlin-reflect). `in` needed the spread form to escape a vararg/Iterable overload ambiguity. Non-Boot JDSL wiring (test `ListingJdslApp`): `JpqlRenderContext` bean + shared `EntityManager` + `KotlinJdslJpqlExecutorImpl(em, ctx, metadata = null)` + `@Import(KotlinJdslJpaRepositoryFactoryBeanPostProcessor)`. 12 JDSL tests on Postgres 17.

**🏆 EXPERIMENT WON — keyset seek through JDSL (`HqlTupleComparisonTest`):** HQL 7 documents tuple comparison; `customPredicate("({0}, {1}) > ({2}, {3})", path(createdAt), path(id), value(ts), value(id))` → Hibernate 7.4 renders `(l1_0.created_at,l1_0.id)>(?,?)` — a real row value, NOT the OR chain — and Postgres plans `Index Scan using listing_created_at_id, Index Cond: (ROW(created_at, id) > ROW(…))`, no Filter. So JDSL + our Cursor + `KeysetPage.fromOverFetch` gets the depth-proof seek that Spring Data's `Window` scrolling (OR chain → Filter walk) cannot. Decision: the pagination JDSL adapter (`pagination-jdsl`: `Jpql.keysetAfter(keys, cursor)` generic over `KeysetKeys`, built on `customPredicate`) is the recommended keyset engine; Spring Data scrolling stays as the zero-code alternative.

**pagination-jdsl built & green (2026-10-20, later; 9 tests on Postgres 17):** first `KeysetKey`/`KeysetKeys` moved from pagination-spring to **core** (Spring-free; core `Direction`; `decode(cursor)` with the two 400s and `cursorOf(values)` now live there so every engine shares them; spring keeps `toSort()` + scroll adapters) and **`SortableFields` now declares `KeysetKey`s instead of names** — ONE order declaration per list gives the sort whitelist, the tie breaker, and `keysFor(sortRequest)`: the client's directions applied, tie breaker last, total by construction. Then the module: `JdslKeyset<E>(sortable) { bind(key, E::prop) }` (compiler-typed, every sortable field must be bound); `Jpql.keysetAfter(request, keys, keyset)` — **same-direction keys → ONE row value via `customPredicate("({0}, {1}) > ({2}, {3})")`** (Hibernate renders `(l1_0.created_at,l1_0.id)>(?,?)`, Postgres `Index Cond: (ROW(created_at, id) > …)`, no Filter — asserted); all-desc → `<`; **mixed directions → OR chain** (correct, walks the index — asserted on `price,desc`); `keysetOrder(keys, keyset)` for `orderBy`; `List<E?>.toKeysetPage(request, keys, keyset)` builds the cursor from the last row's property values. Proven: default sort walk, client sort `price,desc` walk, all-desc walk, filter (`status = open`) ANDed with the cursor in one query, cursor from another sort → `after: is not a valid cursor`, unknown sort field → 400 before any query. This is the recommended keyset engine.

**selector-spring built & green (2026-10-20; 6 MockMvc tests, real MVC context, no Boot):** `@Filtered("<FilterDefinition bean name>") selection: Selection` on a controller parameter; `SelectionArgumentResolver(beanFactory)` looks the definition up by name and parses the WHOLE query string (reserved page/size/after/sort skipped); a `Selection` parameter without the annotation fails with an IllegalStateException naming the method and the fix; `SelectorExceptionHandler` → RFC 9457 400 "Invalid filter" with `parameter`; `SelectorConfiguration` (proxyBeanMethods = false) wires both. Design call: the definition is named per parameter (bean name) so one app serves many lists; a per-list annotation class was rejected (needs kotlin-reflect for objectInstance). Spring 6+ has no NestedServletException — MockMvc throws ServletException with the cause.

## Pagination library — core built & green (0.1.0-SNAPSHOT, 2026-10-19)

Second library in the container: `pagination/` with `pagination-core` (Kotlin, stdlib only, package `io.github.siloverse.pagination.core`) and `pagination-bom`. Own version `0.1.0-SNAPSHOT`, own `:pagination:release` task via the parent convention. Kotlin is switched on by the jvm-library convention's auto-detect (a `src/*/kotlin` dir exists) — no `siloverse.kotlin` property, so the Java messaging modules stay untouched. 43 tests, all AssertJ.

**Types (all public; Awais split them into sub-packages 2026-10-19 — core: `offset` / `keyset` / `policy` / `error`; spring: `config` / `web` / `response` / `util`; tests mirror the packages):**
- `OffsetRequest(page, size)` with `offset: Long`; `OffsetPage(items, request, totalElements)` derives `totalPages`/`hasPrevious`/`hasNext`. A page past the end is a legal, empty page.
- `Slice(items, request, hasNext)` — same `OffsetRequest`; the request says *where*, the result type says *what you paid for* (no `COUNT`). `Slice.fromOverFetch(rows, request)` does the `size + 1` trick and rejects more rows than that (caller wrote the wrong `LIMIT`).
- `Cursor` (value class over one string): sort key values of the last row, each part base64url, joined by `.`; URL-safe, separator-safe, `parts()` round-trips. Typed ↔ string conversion is the adapter's job.
- `KeysetRequest(after: Cursor?, size)`, `KeysetPage(items, request, nextCursor)`; `fromOverFetch(rows, request, cursorOf)` — `cursorOf` lives with the caller because only the caller knows the sort columns. No "before" cursor, no count (YAGNI).
- `PaginationPolicy(defaultSize, maxSize)` — the ONE door from client input: fills the default, **rejects above max (never clamps — the rebuy paginator anti-pattern)**, validates the raw cursor string. Throws `PaginationException(parameter, message)` so the web layer can 400 naming the parameter. Misconfigured policy (default > max) fails with `IllegalArgumentException` at startup, not as a client error.

**Design calls (Awais, 2026-10-19):** `require` + `IllegalArgumentException` inside the value types; the typed exception exists only at the policy door. Spring `Pageable` is NOT used in core — it is offset-only, `Page<T>` JSON is not a stable contract (Spring warns since Data 3.3), and core must work without Spring. `pagination-spring` will hold the one-line `OffsetRequest ↔ Pageable` / `Page ↔ OffsetPage` adapters, the argument resolver, and the 400 mapping. The exhibit test: `KeysetPageTest."a row inserted between pages does not make the next page repeat a row"` — offset shows row 10 twice, keyset does not.

**pagination-spring built & green (2026-10-19, later the same day; 10 tests, real Spring MVC context via `AnnotationConfigWebApplicationContext` + MockMvc, no Boot):** `PaginationArgumentResolver` (controller declares `OffsetRequest`/`KeysetRequest`; reads `page`/`size`/`after`; string→Int here, acceptability in the policy; `?size=ten` → 400), `PaginationExceptionHandler` (`@RestControllerAdvice` → RFC 9457 `ProblemDetail` 400 with a `parameter` property), `PaginationConfiguration` (`@Import` it; `PaginationPolicy` bean overrides `DEFAULT` via `ObjectProvider`), one-line `Pageable` adapters (`toPageable(sort)`, `Page.toOffsetPage`, `Slice.toSlice`), and FLAT response models `OffsetPageResponse`/`SliceResponse`/`KeysetPageResponse` + `toResponse()` — the JSON contract; no nested `request`, cursor is a plain string. Lessons paid: (1) Kotlin classes are final → `@Configuration(proxyBeanMethods = false)` or Spring refuses to subclass (messaging never hit it, it is Java); (2) Spring Data's `Page<T : Any>` forces `<T : Any>` on the adapters; (3) MockMvc `jsonPath` needs `json-path` on the test classpath, and its `isArray`/`isString` matchers also need Hamcrest — assert values instead of adding Hamcrest; (4) Boot's test starter hides both. Factory spelled `fromOverFetch` on Slice and KeysetPage (Awais's spelling, aligned).

**Keyset proving ground, step 1 — hand-written SQL on real Postgres 17 (2026-10-19 night; `pagination-spring/src/test/.../keyset/KeysetSqlProvingGroundTest`, 7 tests, Testcontainers, no JPA).** 5000 listings ten-per-second (every `created_at` shared by ten rows), 0–3 photos each, index `(created_at, id)`. Five findings, each pinned by an assertion:
1. **Tie breaker is correctness, not style.** `WHERE (created_at, id) > (?, ?) ORDER BY created_at, id` visits all 5000 exactly once, in index order. `WHERE created_at > ?` with page size 25 (ends mid-group) SKIPS the rest of the boundary group every page.
2. **Row-value comparison seeks.** EXPLAIN: `Index Only Scan using listing_created_at_id`, `Index Cond: (ROW(created_at, id) > ROW(...))`, no Sort, no Filter, table never touched. Same cost at any depth — the whole point of keyset.
3. **The OR chain does NOT seek on Postgres.** `created_at > ? OR (created_at = ? AND id > ?)` (the form ORMs write, Hibernate included) plans as Index Only Scan + `Filter:` and no Index Cond: it walks the index from the start and discards until 25 pass. Deep page = long walk = offset cost through a side door. ⇒ Step 2 must check what SQL Spring Data `Window`/`KeysetScrollPosition` emits; if it is the OR chain, the JPA adapter is not enough and the keyset query must be native SQL with the row-value form.
4. **Postgres ROUNDS timestamps to microseconds** (not truncates): `.123456789Z` stored as `.123457Z`. A cursor built from the application's Instant points at a row that does not exist ⇒ **always build the cursor from the value the database returned.**
5. **Collection join + LIMIT pages rows, not parents**: `listing LEFT JOIN listing_photo … LIMIT 10` = 10 rows, < 10 distinct listings. Fix: page the parent in a subquery, then join children (10 distinct, equal to the first 10 of the total order). This is the SQL root of Hibernate's "firstResult/maxResults specified with collection fetch; applying in memory".

**Keyset proving ground, step 2 — Spring Data JPA 4.1 / Hibernate 7.4 on the same Postgres (2026-10-20; `KeysetJpaProvingGroundTest`, 3 tests; fixture shared via `ListingFixture`; every SQL captured by a Hibernate `StatementInspector`).** Three answers:
1. **`Window` + `ScrollPosition.keyset()` is CORRECT**: `findFirst25ByOrderByCreatedAtAscIdAsc(position)` walks all 5000 once, in order, ties handled (Spring Data puts every sort column into the position).
2. **…but Hibernate writes the OR chain**: `where created_at>? or created_at=? and id>? order by … fetch first ? rows only`. EXPLAIN on that exact statement: `Index Scan using listing_created_at_id` + `Filter:`, no Index Cond — the index walk from step 1 finding 3, confirmed through the ORM. (Index Scan, not Index Only, because `title` is selected.) ⇒ keyset through Spring Data is right but not depth-proof on Postgres.
3. **Hibernate 7 no longer pages in memory for a collection fetch.** `@EntityGraph(photos)` + `Pageable` produced `from (select … order by … offset ? rows fetch first ? rows only) l1_0(…) left join listing_photo …` — the parent is paged in a derived table, then joined: exactly step 1's fix, done by the ORM. No HHH90003004, no second select, 10 distinct listings with their photos.

**Decision for step 3 (proposed, Awais to confirm):** the adapter in `pagination-spring` is `KeysetRequest ↔ KeysetScrollPosition` and `Window ↔ KeysetPage`, so a repository method with `ScrollPosition` works with our `Cursor` and policy. This is correct and simple. Depth-proof seeking (row-value `Index Cond`) needs a native query; provide that as a documented pattern, not library code, until a real list is deep enough to need it.

**Step 3 — the adapter, built & green on the real database (2026-10-20; `spring.keyset` package in pagination-spring; `ScrollAdaptersTest`, 7 tests).** `KeysetKey<T>(property, direction, encode, decode)` with factories `uuid/long/string/instant/offsetDateTime`; `KeysetKeys(vararg keys)` = the sort of one list, written once next to the list — `sort()` gives the Spring `Sort`, so the cursor and the ORDER BY cannot drift. `KeysetRequest.toScrollPosition(keys)`: null cursor → `ScrollPosition.keyset()`; else parts decoded in key order → `ScrollPosition.forward(map)`; wrong part count → `PaginationException("after", "does not belong to this list")`, undecodable part → `"is not a valid cursor"`. `Window.toKeysetPage(request, keys)`: next cursor encoded from `positionAt(last).keys` — the values AS LOADED, which settles step 1 finding 4 for free. Composition proven: `repository.findBy(spec) { it.sortBy(keys.sort()).limit(size).scroll(position) }.toKeysetPage(...)` with a `title like 'listing 1%'` Specification walks exactly the filtered set in order — filter + cursor in ONE query (Awais's question: the filter says which list, the cursor says where in it; they AND). Decision confirmed: no native query in the library; the row-value form is journaled as the deep-page optimisation. Shared test context `ListingJpaApp` (no Boot). Kotlin repository interfaces need `kotlin-reflect` on the classpath (Spring Data reads them through it). `findBy`'s lambda needs an explicit `FluentQuery.FetchableFluentQuery<T>` type in Kotlin.

## Tracing through the broker (1.0.11-SNAPSHOT, 2026-08-29) — the milestone money shot

- **Producer:** `EnvelopeHeadersContributor` SPI in `core.transport` (Map-only, dependency-free); `TracingHeadersContributor` in `spring.tracing` injects W3C `traceparent` via Micrometer `Propagator` at PUBLISH time — inside the caller's transaction — so **the outbox persists causality** (verified: traceparent in `messaging_outbox.headers` JSONB, matching the live request trace). Null-context guard: no active span → untraced message, never an NPE. `EnvelopeFactory` is now constructed once (Spring bean) and threaded through BOTH buses — single definition of envelope construction preserved.
- **Consumer:** `MessageDispatcher` widened to `(definition, headers, message)` AND extracted to interface + `DefaultMessageDispatcher` in the same breaking window (rule: bundle breaks; the concrete class was the house-style anomaly — every other seam is an interface). `TracingMessageDispatcher` (true delegate decorator, no inheritance) extracts the remote parent, names the span `<consumer-id> consume`, wraps the invocation (`span.error` on throw — poison messages show red in Tempo), ends in finally.
- **AMQP boundary lesson:** broker returns published String headers as `LongString` in a `Map<String,Object>`, and `getHeaders()` is null for headerless messages — `RabbitMqMessageListener.stringHeaders()` owns the translation (adapter's job).
- **EIP mapping** (the project's founding goal, closing a loop): Envelope Wrapper carries it, Correlation Identifier is what traceparent is, Message History is what Tempo reassembles — "tracing is Message History stored out-of-band." Dispatcher wrapper is GoF Decorator, not EIP.
- Verified end-to-end: one trace, 16 spans, three services, ~126ms visible relay gap before `user-registered-notifier consume`.
- Library debug logs: gate expensive serialization behind `isDebugEnabled` (arguments to `{}` are eager); prefer messageId/type over payloads — hosts' PII is not the library's to print.

## Retry tiers v1 — constant delay (1.0.11-SNAPSHOT, 2026-08-30/31) — green, published, VERIFIED LIVE (poison test in notification-silo 2026-08-31: annotation TTL on broker, x-death 9+9, parked at exactly maxAttempts with x-parking-cause, traceparent intact — details in notification-silo/CHECKPOINT.md)

- **Topology** (`RabbitMqTopologyDeclarer`): per consumer, three queues declared dlq → retry → main. Main dead-letters (default exchange, no extra exchange objects) into `.retry`; retry carries `x-message-ttl` = the policy delay and dead-letters expired messages back to main. `.dlq` is terminal (no DL args, no loops). Circular retry↔main pointer is safe: a newborn queue is empty, nothing can expire out of it. **Queue arguments are immutable** — changing them against live queues = 406 PRECONDITION_FAILED; dev migration = delete old queues in the management UI, declarer rebuilds.
- **Policy** (`retry/RetryPolicy`, `retry/RetrySettings`, `consumer/RabbitPolicy` in messaging-rabbitmq — REDESIGNED 2026-08-31, supersedes the override map): `maxAttempts` counts TOTAL broker deliveries (x-death), constant `delay`. Per-consumer policy is now declared in code via the companion annotation `@RabbitPolicy(maxAttempts, delayMillis)` next to `@Consumer` — Awais's call after a full grilling (deploy-crash/406, test-timing, precedence, layering, partial-override, consistency all answered): locality won over live-tunability, with eyes open. Layering preserved: the annotation lives in messaging-rabbitmq (`consumer` package, mirroring core's `consumer.Consumer`) — core never learns broker vocabulary; putting fields on core's `@Consumer` was rejected (and Java can't extend `@interface` anyway). Name deliberately roomy — admission rule in its Javadoc: per-consumer, RabbitMQ-specific, developer-declared, sane system default (prefetch is the expected future tenant; fields only when needed). Precedence ladder: **annotation > `messaging.retry.default-policy` yml > `RetrySettings.DEFAULT` (3, 10s)** — no yml per-consumer overrides (map deleted, and with it the unknown-ids validation: annotations can't name a wrong consumer). Sentinel `-1` = inherit per FIELD (also the growth mechanism: only defaulted annotation elements can be added without breaking call sites); yml default-policy is all-or-nothing, no three-way merge. `RetrySettings(defaultPolicy)` + `policyFor(ConsumerDefinition)` is the single referee — reads the annotation off `definition.method()`, merges, and translates RetryPolicy's IAE into `MessagingConfigurationException` naming the consumer (RetryPolicy owns validity; policyFor adds the culprit; fails at boot because the declarer calls it per consumer). Accepted costs, in writing: per-consumer tuning is a rebuild; `@RabbitPolicy` off a `@Consumer` method is silently inert; changing `delayMillis` is a broker migration (406 — Javadoc warns in bold). Declarer test proves annotation→TTL on a real broker (400ms override under a 10s default, 5s await window = the teeth); poison test proves annotation beats default on the handler side (maxAttempts 2 ⇒ exactly 4 invocations, 6 under the default).
- **Failure seam** (`retry/FailedDeliveryHandler` + `RetryingFailedDeliveryHandler`): listener keeps the one immediate in-process retry (requeue nack, invisible to x-death); a redelivered failure goes to the handler, which counts prior rejections from x-death (grouped by queue+reason, only main-queue rejections count) and either nacks into `.retry` or **parks by active republish** — the main queue's DL routing is fixed, a final nack cannot choose `.dlq`, so parking is confirmSelect + publish + waitForConfirmsOrDie + ack-original. At-least-once parking; the rare duplicate is absorbed by the dedup inbox. Parked copy carries `x-parking-cause` alongside x-death.
- **Layered responsibility:** inbox = exactly-once effect · listener = one immediate retry · topology = backoff schedule · x-death = attempt counter (broker-owned — a component that could roll back its own counter can't be trusted with it) · DLQ = terminal + human. Escalating tiers = v2 IOU (needs active republish per tier; a static DLX can't branch on count).

## RabbitMQ adapter — decisions locked (2026-08-14)

- **Connection ownership:** services provide CONFIG only (host, port, username, password); the library handles connections internally. Two layers: the connector (settings record → configured auto-recovering `Connection`; the WIRING owns closing — Spring bean `destroyMethod="close"` later) and the transport (borrows `Connection`, owns its `Channel` + confirm state). Constructor-does-I/O is deliberate: broker unreachable = loud boot failure, same philosophy as registry freeze in BFPP. Connection must be owned ABOVE the transport because the future consumer side needs channels on the SAME connection (RabbitMQ model: one connection, many cheap channels).
- **One shared transport instance** for `DefaultAsynchronousBus` + `OutboxRelay`. Interleaving at message granularity is harmless (independent streams; relay ordering is within-its-own-sequence and it's single-threaded). Splitting instances = wiring qualifiers bought against unmeasured contention; two-line change if ever measured.
- **Declaration ownership (settled 2026-08-14):** each side declares what it TOUCHES — publishers declare exchanges (one per name in their frozen `MessageNameRegistry`; idempotent by AMQP contract), consumers declare exchanges + their queues + bindings. Resolves the zero-consumer conflict: without publisher declaration, a LEGAL zero-consumer event would 404 and kill the transport. The empty exchange does two jobs: publisher's stable public address (consumers bind/unbind freely) and the broker-enforced boundary between "nobody cares" (acked no-op, legal) and "no such message type" (404, loud). Queues belong to consumers ONLY — an unconsumed queue accumulates forever; an idle exchange is a free routing-table entry. NEW CONFIG KNOB: the consuming service must supply its service name (queue prefix) — parameter on `declareConsumerTopology` for now, promoted to a settings object when a second consumer of it appears.
- **Topology: exchange-per-message-type, fanout; exchange name = routing key = wire name from `MessageNameRegistry`.** Chosen over one big topic exchange for fail-fast: typo'd type → 404 channel error → send throws; in a topic exchange a typo'd routing key silently drops. Binding = subscription (what consumer startup declaration will do). Routing key is informational under fanout (wire self-description, uniform column mapping, forward-compat) — if exchange and key ever differ, someone changed an exchange type and the transport mapping needs revisiting.
- **`mandatory` flag NOT set — decision, not oversight.** Unroutable = acked and dropped, correct because zero-consumer events are LEGAL; mandatory+ReturnListener would flag legal events as failures and drag kind-awareness into the kind-agnostic publish path (returns carry no seq numbers — correlation would need messageId matching). Command-must-have-consumer is enforced at consumer-startup topology declaration, not in the publish path.
- **Failure contract is ASYMMETRIC (javadoc + every error message teaches it):** return = 100% durably published (persistent message, durable-queue ack). Exception = NOT-CONFIRMED-published, two flavors the messages distinguish: local publish failure = "not published, retry"; timeout/interrupt/channel-lost = "outcome UNKNOWN — treat as unpublished and retry (consumers dedup by message id)". The symmetric version ("exception = certainly not published") is exactly-once and does not exist.
- **Exception tiers at this layer (settled 2026-08-14):** tier is chosen by WHAT THE FIX IS, not when it fires. Channel-open failure at transport construction = `MessagingException` (environmental). Connector: `AuthenticationFailureException` → `MessagingConfigurationException` naming host/port/username, NEVER the password (fix = correct config); other `IOException`/`TimeoutException` → base `MessagingException` (fix = operational). `MessagingConfigurationException` gained a `(String, Throwable)` ctor for this.
- **Channel-death policy gap (recorded, undecided):** client auto-recovery (on by default) heals CONNECTION-level failures — sends fail during outage, work after, relay retries free. It does NOT resurrect channels closed by protocol errors (the 404): after that this transport is dead until restart. Defensible (broken topology = loud permanent failure) — decide policy when topology declaration lands.
- **Throughput ladder (parked, in order):** batched confirms for the relay (publish N, await all — needs port widening + stop-at-first-failure rethink) → `sendAsync(Envelope)` → `CompletableFuture<Void>` (completion = durable ack, same contract deferred; impl is already there privately; javadoc must fence blocking in callbacks — they run on the connection I/O thread) → channel pool (only if stuck blocking AND concurrent; honest competitor then is Spring AMQP's CachingConnectionFactory) → separate publish/consume connections (about broker flow control, not throughput: memory-pressure throttling of publishing connections must not stall consumers — adopt when consumer side lands). REJECTED: channel-per-call (4 round trips per message + broker channel churn), connection pool (AMQP connections multiplex — pooling them is a JDBC habit), ThreadLocal channels (leaks + virtual-thread explosion).
- **Not integration-testable, accepted:** real broker nack (only on internal broker failure — translation covered via shutdown/dead-connection paths); lost-ack-on-healthy-channel (needs Toxiproxy — parked); publish-lock atomicity (reviewed, not tested — no nondeterministic concurrency tests).

## ✅ Gate closed — crash story answered (2026-08-13)

Unstamped row after relay restart is ambiguous (never-published vs published-but-unstamped look identical; relay can't ask the broker). Relay REPUBLISHES — duplicate beats loss. Consumer sees byte-identical duplicates, same `message_id` = dedup key.

**`TransactionAwareAsynchronousBus` contract (javadoc must promise):** committed tx ⇒ delivered **at least once**; duplicates possible; consumers must be idempotent; rolled-back tx delivers nothing (outbox row rolls back with business data). Exactly-once delivery = myth without 2PC; real thing is at-least-once + idempotent consumption.

**`AsynchronousBus` rationale (decided):** direct-to-broker, NO outbox/relay/DB in path. Exists for (1) stateless publishers (no tx to join — outbox structurally unusable), (2) self-healing messages (cache hints, telemetry, heartbeats) not worth the outbox premium. Litmus: message asserts a DB-committed fact → tx-aware bus; otherwise → async bus. Contract: **at-most-once** wrt crashes (may await broker ack, throw on nack; crash before ack = silent loss). Ghost-message trap: publish inside a rolled-back tx announces a state that never happened — javadoc warns.

**Message naming — LOCKED, do not reopen (litigated 6×; 5× 2026-08-13, reopened 2026-08-14 as "class FQN as routing key, renames managed by rollout planning + team-lead review" and HELD: messages in flight outlive deploys — outbox rows and queued messages carry the old name after a rename, and the no-`mandatory` acked-and-dropped design makes the resulting loss SILENT and review-proof; the registry makes class renames a non-event instead of a distributed migration):** wire name comes from a `MessageNameRegistry` (core class: builder, `register(Class, String)`, `freeze()`, `nameOf(Class)`). Each service ships a static registry INSIDE its messages/contract jar (e.g. `OrderSiloMessages.names()`) so publisher and consumers read the same map — classes and names travel together. Name convention: `<service>.<message>` lowercase-dashed (e.g. `order-silo.order-created`) — a style rule for humans, never computed. REJECTED: `@MessageName` annotation (user preference; delete the typed file), class-name derivation (dash illegal in packages, rename = silent loss — failed twice in user's own examples), instance-level MessageProvider naming (no instance exists at startup binding time). Wire identity must be static per type, resolvable from `Class` alone. Failures: unregistered class → `MessagingConfigurationException` at first publish (publisher) / at startup binding (consumer); blank name or duplicate class → builder throws. Service module layout agreed: `silo` (app) / `messages` (contract jar) / `web` (DTOs); dashes legal in Maven coordinates, not in Java packages. "MessageProvider" = app-side factory building message objects — user's own code, no library involvement; bus signature stays `publish(Event)`/`send(Command)`.

**Ghost-trap enforcement (decided):** NO runtime tx detection — trap is semantic (message meaning), not mechanical (tx active), so a runtime guard false-positives on legit uses (e.g. metrics inside `@Transactional`) and would drag spring-tx into the publish path. Enforcement = javadoc + code review; static-analysis suggestion parked.
